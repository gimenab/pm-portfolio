PM-AI-Workflow: Automating the Busywork of Project Management

A system of AI skills and subagents that handles the repeatable, structured work of project management — ticket intake, sprint reporting, stakeholder updates — so strategic time stays protected.

01 /

The Problem & Value Proposition

The Operational Tax

PMs lose a large share of their week to repeatable admin work — formatting tickets, assembling reports, chasing updates, drafting scope documents and more — time that competes directly with strategy, discovery, and prioritization.

PM-AI-Workflow's Value Proposition

Structured, repeatable project management work shouldn't compete with strategic thinking for the same hours. A system of AI skills and subagents takes over the high-volume, structured parts of the role — from ticket intake to scope analysis — and frees time for the judgment calls only a project manager can make. Every skill is plain Markdown that any AI agent able to read the repo can follow, and it is auditable in git. The SOW intake prompt was validated on Claude, ChatGPT and Gemini.

02 /

How It Works

Every skill and subagent in the system follows the same three-step flow, turning unstructured input into standardized, ready-to-use output:

RAW INPUT A problem description or live sprint data
AI SKILL / SUBAGENT Guided intake or autonomous analysis
STANDARDIZED OUTPUT A complete Jira ticket or a ready-to-share report
Example — SOW: from brief to Discovery

A founder brief goes through four skills. First, sow-drafting turns it into a Statement of Work, and sow-intake-analysis reads that SOW critically and flags what is missing:

founder-brief.pdf

Excerpt from the original brief, translated from Spanish. It has no timeline, budget, stakeholders or acceptance criteria.

sow-intake-analysis — 31 gaps flagged
No sponsor, lead or decision authority → Who decides on scope changes and approves the MVP?
Timeline, budget and resourcing are all absent → What are the deadline, budget and available team?
Platform → Which platform(s) must the MVP support?

+ 28 more, each with why it matters and a clarifying question.

After the alignment meeting decides those gaps, the updated SOW goes through the two skills that prepare Discovery:

Structured Ticket Intake

Conversational skills that turn a raw task or story description into a complete Jira issue — acceptance criteria, assumptions, story points — following the team's exact format, enforcing consistency the team wouldn't otherwise have.

Sprint Reporting

Subagents that read live sprint data and generate the sprint health report, retro insights, and release notes that used to be assembled by hand.

Strategic Planning

Agents that keep OKRs, the roadmap, and a quantitatively-prioritized backlog up to date as living documents instead of static slides.

Stakeholder Communication

Turns sprint and OKR data into an executive-ready status update, without exposing stakeholders to raw Jira noise.

SOW: from brief to Discovery

Four skills that take a Statement of Work from the client brief to Discovery: one drafts a formal SOW from an unstructured brief, one critically reads it and flags every gap — timeline, budget, stakeholders, acceptance criteria — and one turns the SOW agreed at the alignment meeting into a Discovery plan: a persona framed as a hypothesis, the MVP feature matrix and an agenda built from the open questions. During Discovery, a fourth skill walks the core loop with the client and turns each “what happens if...?” into a decision with an owner, before any user story is written. The reading prompt was validated across three different LLMs for consistency, not just tuned for one.

Example • work-item-user-story

Raw note → 2 user stories

The note mixed two needs, so the skill split it into two stories. The complete draft the skill produced, as generated. Nothing was created in Jira.

User Stories: Daily Tasks and Bank of Minutes

Status: Draft. Nothing has been created in Jira. Items marked (proposed) are inferred, not stated by the requester.

US 1: View daily tasks

Title

USER STORY [DAILY TASKS] As a user I want to see today's pre-loaded tasks and my own difficult task so that I know what I have to do today

Description

As a user, I want to see the day's pre-loaded tasks (up to three) together with the difficult task I chose earlier, if any, so that I know exactly what I have to do today.

ID Criterion Given When Then
01 View pre-loaded tasks Tasks are pre-loaded for today I open the daily tasks I see the pre-loaded tasks for the day, never more than three
02 Fewer than three tasks Fewer than three tasks are pre-loaded for today I open the daily tasks I see only the tasks that exist, with no empty placeholders (proposed)
03 View my difficult task I chose one task for today and marked it "difficult" I open the daily tasks I see it as an additional task after the pre-loaded ones, so up to four tasks in total
04 No difficult task I have not chosen a difficult task for today I open the daily tasks I see only the pre-loaded tasks
05 Difficult task is distinguishable My difficult task is in the list I open the daily tasks I can tell it apart from the pre-loaded tasks (proposed)
06 Load failure The tasks cannot be loaded I open the daily tasks I see an error message and no partial or incorrect list (proposed)

Assumptions

  • The system pre-loads the day's tasks (up to three) before the user opens the screen. How they are selected is out of scope.
  • The user can choose one difficult task per day, regardless of category. This limit is enforced by the existing flow, so the screen never shows more than one.
  • The maximum of three applies to pre-loaded tasks only. The difficult task is an additional fourth item.
  • Creating or editing tasks and the "difficult" marking flow are out of scope.

Additional fields

  • Story Points: 2 (proposed). Estimated Points auto-populates with the same value.
  • Labels: daily-tasks, task-list (proposed)
  • Priority: Medium (proposed)
  • Sprint: Backlog
  • Assignee: Unassigned

US 2: Automatic minutes on task completion

Title

USER STORY [DAILY TASKS] As a user I want the earned minutes to be added to or removed from my bank of minutes automatically when I mark or unmark a task as complete so that I don't need extra steps and my balance is always correct

Description

As a user, I want the minutes of a task to be added to my bank of minutes automatically when I mark it as complete, and subtracted if I unmark it, so that I don't need extra buttons and my balance stays correct even if I mark a task by mistake.

ID Criterion Given When Then
01 Complete a task, minutes credited A task in my list is pending I mark it as complete Its fixed minutes value is added to my bank of minutes automatically, with no extra button or confirmation
02 Complete the difficult task My difficult task is pending I mark it as complete Its fixed minutes value is added to my bank of minutes automatically, the same as any other task
03 Visible feedback I just completed a task The minutes are added I see the task as completed and my updated bank of minutes (proposed)
04 Unmark by mistake, minutes subtracted A task is completed and its minutes were added I unmark it as complete The same minutes are subtracted from my bank of minutes automatically, and the task returns to pending
05 No double credit A task is already completed I trigger completion again or reload the screen The minutes are not added a second time (proposed)
06 Repeated toggling stays consistent I mark and unmark the same task several times I end on either state The bank of minutes equals the balance before the task, plus the task's minutes only if it ends as completed (proposed)
07 Operation failure I mark or unmark a task but the change cannot be saved The operation fails I see an error message, and the task state and bank of minutes remain consistent with each other (proposed)

Assumptions

  • Each task has a fixed minutes value, and the rule that defines it already exists. This US does not change it.
  • The difficult task earns its minutes with the same fixed-value logic as other tasks, with no extra multiplier, unless its own value says otherwise.
  • The bank of minutes already exists as the user's balance. This US covers only crediting and debiting it on completion changes.
  • The amount subtracted on unmarking is exactly the amount that was credited, so the balance can't go below what it was before the task.
  • The rules for using or redeeming minutes are out of scope.

Additional fields

  • Story Points: 3 (proposed). Estimated Points auto-populates with the same value.
  • Labels: daily-tasks, minutes-bank (proposed)
  • Priority: Medium (proposed)
  • Sprint: Backlog
  • Assignee: Unassigned

Open point

  • The difficult task is assumed to have its own fixed value like any other task, not a bonus. If it earns more, criterion 02 in US 2 needs a specific rule.

Task: Create 10 tasks with time bank minutes

Status: Draft. Nothing has been created in Jira. Items marked (proposed) are inferred, not stated by the requester.

Type: Task
Platform: Jira (assumed)
Project: none (placeholder, no real project)
Title: [DAILY TASKS] Create 10 tasks across health, home and work with bank minutes (proposed)

Description:
Create a set of 10 tasks distributed across the categories health, home and work. Assign each task a fixed number of minutes that is added to the time bank when the task is completed.

Objective: Provide a ready-to-use catalog of tasks, each with a fixed time bank reward.
Context: The daily tasks feature needs tasks to pre-load and a minutes value per task. Without them, there is nothing to display or credit.
Scope:
- Includes: 10 tasks (proposed split: 4 health, 3 home, 3 work). Each has a title in `[MODULE] Verb + object` format, a short description, an estimated time, labels and a fixed minutes value.
- Excludes: the logic that pre-loads tasks each day, the crediting or debiting of the time bank, and creating the tasks in Jira.

Done when (proposed):
- There are exactly 10 tasks and all three categories are represented.
- Every task has a fixed minutes value.
- Minutes roughly reflect effort, so longer or harder tasks earn more.

Estimated time: 60 min (proposed)
Priority: Medium (proposed)
Labels: daily-tasks, task-catalog (proposed)
Story points: not set
Destination: Backlog
Assignee: Unassigned
Components / Fix Version / Sprint: not set
